# Autonomous coordinator decisions

Implementation status: project and assignment records use shared locked JSONL persistence. The coordinator plugin provides scoped host admission, persisted identity/pause, and cold-start Team discovery. Automatic independent-task dispatch is implemented under explicit execution configuration; verified dependency scheduling passes a real-Git diamond DAG; in-process midway restart passes the process gate; opt-in candidate retention and a host-only integration review gate are now wired; broader recovery remains unfinished. The remaining decisions below constrain subsequent slices; they are not claims of implemented behavior.

## Durable authority

`projects.jsonl` is an authoritative, versioned registration journal, not a cache. It contains immutable project identities, canonical repository identities, target branches, verification policy, capacities, and team-session references. Project policy currently has revision 1; updates need explicit events and revision checks in a later slice. Session logs remain authoritative for the existing team task board, roster, and mailbox.

The coordinator's `acceptTask` path requires a committed registration before calling the existing durable task board. Registration is granted by the exact live Lead only for its own Team. An interrupted registration may leave an empty project, but accepted tasks cannot depend on an uncommitted catalog entry. Existing unregistered sessions remain usable in interactive mode; autonomous adoption must be explicit and validated. Startup reads every registered Team using the published persistence inspection API and the existing Team projection. Missing or invalid sessions produce durable deduplicated reconciliation failures and remain in the project view. No Lead is materialized just to discover work.

Journal writes are serialized and synced before acknowledgement. An uncertain write stops further admission through that instance. Replay requires contiguous sequence numbers and validated versioned records; malformed, unsupported, or incomplete records fail with instructions to restore a consistent backup. Existing session history is untouched. No new published-runtime patch is needed for this catalog.

## Service authority and ownership

Every journal now acquires an exclusive nonblocking Linux `flock` on its open file description before reading or writing. The inherited descriptor used by the short-lived `flock` command shares the parent's lock; the parent retains it until close or process death. A separate-instance test and a three-process test verify exclusion and release after SIGKILL. This requires Linux and util-linux `flock`; other platforms or missing locking support fail explicitly. Journal files must not be replaced or unlinked while an owner is active.

`WorkspaceCoordinator.open` acquires `coordinator.jsonl` before opening subordinate stores. This journal holds its immutable generated coordinator identity, revisioned project pause controls, and Team reconciliation results. A second coordinator fails before opening those stores. The plugin awaits initial reconciliation before publishing `ctx.workspaceCoordinator`, serializes operations, and uses nonoverlapping periodic scans. Disposal clears the timer, cancels inspection, awaits operations, closes the catalog, and releases coordinator ownership last. Execution disposal drains managed DSH children and disposes only coordinator-restored Lead handles before releasing journals/policies. Drain failures retain ownership rather than allowing a competing writer; per-runtime DSH drain observations now have a 30-second deadline. The pending drain is retained and rejoined on reconciliation; a timeout does not release capacity or prove termination. A failed coordinator close can be retried: its shutdown fence remains set, ordinary operations and managed wakeups stay rejected, and concurrent close callers share one operation. A retry rejoins pending drains before releasing ownership. Whole-operation startup/shutdown bounds and external process-tree teardown remain unfinished.

The coordinator has a persisted identity and a narrowly scoped grant covering registered projects. Its mutations validate exact live Lead membership and registered Team scope; unrelated and fabricated Agents are rejected. Operator controls for projects without a live Lead still need their own authenticated UI/RPC authority. Worker restoration may use real session handles through supported runtime APIs; it must not fabricate Agents. Future unattended execution operations must enforce project scope and assignment generations.

Repository identity is the real path of `git rev-parse --path-format=absolute --git-common-dir`, so linked worktrees share identity. One project owns each repository/target pair, with multiple teams attached to that project. M4 integration serialization must use that identity across teams. Moving a repository needs an explicit relocation procedure; it must not silently create a second owner.

## Assignment and completion requirements

Worker identity, execution attempt, assignment, workflow, escalation, and cross-project batch IDs have distinct branded types. `AssignmentStore` records one authoritative active assignment per project/team/task. Assignment intent and its generation become durable before the caller provisions its persisted runtime ID. Runtime IDs cannot be reused, including after termination. Worker IDs can be reused for later attempts. All worker mutations compare attempt identity, generation, and revision.

`assignments.jsonl` retains the immutable transition events. Replay reconstructs current attempts and validates every legal transition and ownership invariant. Reports and checkpoints do not terminate an attempt or accept its task. All nonterminal attempts, including provisioning and stopping, consume global and project capacity. Terminal records remain queryable and do not consume capacity. The coordinator now reserves through this authority before invoking worker provisioning.

`DshAssignmentRuntime` now provides the host bridge to Team provisioning. It resolves the persisted attempt and exact parent Agent, uses `spawnReservedTeammate` with the recorded runtime ID, and sends assignment identity plus checkpoint in the worker prompt. Team admission rejects live, persisted, or concurrently provisioning runtime collisions before adding a roster entry. The adapter serializes operations and treats a current active start as idempotent. A preexisting roster child is admitted only if its parent and exact assignment prompt match.

The adapter requires matching latest turn-start/end boundaries before observing persisted completed-turn text as a worker report, leaving the task pending. Older completion cannot override a later unfinished turn. The installed persistence inspector additionally synthesizes interrupted-turn closers; a stop reason takes precedence over retained old report text in recovery status. Cancellation and retirement use the published `drainContinuableChildren` contract, await release, confirm registry absence, and persist the stop receipt. Uncertain ownership is refused before draining another runtime and retains capacity for reconciliation. The coordinator's periodic scan now invokes this adapter for independent ready work and observes existing attempts. Stopping attempts are reconciled before checking registry residency, so a still-resident worker can finish its pending cancellation. Drain deadlines clear their observation timers and retain the underlying operation; independent workers can still reconcile after the deadline. The coordinator enables bounded interrupted-turn continuation; configurable policy and replacement-attempt handoff remain required.

Team spawning and mailbox wakeups separately share a transactional `maxConcurrentMembers` limit, default eight. Durable provisioning entries, live registered Agents, and in-flight wakeup reservations consume slots. Resident Agents retain capacity until registry disposal, which the published AgentLoop emits after driver quiescence. Failed provisioning also triggers capacity retries. Capacity-blocked messages stay in the existing durable mailbox and retry when a slot becomes available. `maxMembers` remains a separate immutable-name history guard, default 4,096; explicit existing settings retain their meaning. No historical names or references are removed. Tests prove nine actual worker responses complete sequentially at capacity two, simultaneous spawn claims reserve only two slots, and blocked wakeups retry once capacity is freed.

Replacement requires authoritative shutdown/fencing evidence; elapsed leases alone cannot free write authority. `retire` is intended only for the coordinator's trusted provider adapter, not a model tool. The DSH bridge now authors these receipts after exact-parent drain and registry checks; external-provider observations remain M9 work. The store validates the receipt's identity and shape; it does not independently inspect processes. Terminal attempts retain their last checkpoint, result, and stop evidence.

Worker reports, submissions, verification, and accepted integration will be separate states. Code tasks cannot satisfy dependencies or complete batches until integration is verified. Non-code tasks require an explicit auditable acceptance policy. Publication workflows require their configured external authorization gate.

## Execution policy and fencing

Optional coordinator `execution` configuration specifies model provider, model ID, and global concurrent capacity. Worktrees are required. The coordinator restores only catalog-authorized real Lead handles, validates their repository cwd and model against policy, and persists an assignment before provisioning a worker. Project capacities remain catalog-owned. Pending tasks enter `dispatch.jsonl` before eligibility checks, including while execution is disabled or the project is paused. Each request has a stable journal order, priority, and revision. Among eligible projects, the least recently selected project gets the next turn (initial ties use earliest request order); within that project, descending priority then ascending order select the task. This gives each continuously eligible project turns even when another has a high-priority backlog. `dispatchIntervalMs` persists pacing through the last selection timestamp; a backwards wall clock holds dispatch until it catches up. Priority changes require the authorized project Lead, a matching request revision, and no prior assignment.

Selection is persisted before reservation but does not consume the request. After a crash in that gap, the request can be selected again after pacing permits. After a reservation exists, assignment history excludes it from new selections and runtime reconciliation handles the existing identity. Fairness records may advance without a provisioned worker, which avoids allowing a failed project to monopolize selection. Serialized coordinator scans remain the transaction boundary between selection and assignment reservation. Dependency acceptance and bounded retry/backoff remain M3 work.

`execution.jsonl` retains deduplicated work-specific blockers. Known failures before runtime start retire the reservation with a never-started receipt, freeing capacity for unrelated work. Uncertain prior side effects retain ownership for reconciliation. Existing terminal attempts are not automatically recreated, so failed work requires the upcoming retry controls. A successful worker report still leaves its code task pending for verified integration.

The coordinator always opens its assignment journal and installs managed-work policies, even when execution is disabled. Policies run inside Team task mutation and wakeup admission transactions. Registered managed tasks reject ordinary direct mutations; terminal/stopping attempts reject wakeups. This prevents configuration changes from silently restoring old worker authority. Verified acceptance operations and authenticated retry/cancellation controls still need dedicated service paths.

### Dispatch status

`CoordinatorView.dispatchStatus` derives typed blocker codes and details from the same eligibility function used for admission. Requests are ready, waiting, assigned, finished, cancelled, or accepted; finished describes the attempt, never task acceptance. Reports retain an awaiting-acceptance blocker and stopped attempts without reports retain a recovery-required blocker. Recorded execution diagnostics remain visible alongside those states. Queued work can show all applicable blockers, including global and project capacity simultaneously, and the persisted pacing timestamp. Views are detached snapshots and reading them does not advance scheduling. The opt-in coordinator tool plugin exposes status, pause/resume, and priority in exact Lead scopes. Team Remote descriptors expose project-scoped scheduling and scheduling controls through strict browser-safe schemas. Both paths use coordinator project grants and revision checks; unrelated Leads cannot inspect or control another project. Global authenticated workspace-operator controls and retry remain required.

### Cancellation

A revision-checked `dispatch/cancelled` event persists the reason before attempting worker shutdown. The request is permanently excluded from selection and managed wakeups; its task remains pending for audit rather than being declared accepted. Active cancellation uses the existing assignment stop/drain/retire path, retaining capacity while termination is unconfirmed. Reconciliation prioritizes cancellations over project pause and automatic-admission configuration. With execution disabled and an unopened Lead, restoration still requires configured execution authority; the cancellation remains durable and blocked. Reserved attempts whose runtime ownership cannot be established retain capacity for explicit repair. Cancellation never removes worktrees or artifacts. The model cancellation tool and Remote control action use the same host operation.

### Pinned integration admission

`TeamService.enqueuePinnedIntegration` is a host-only foundation for coordinator submission. It takes a stable integration ID and exact repository, source commit, target branch and verification commands. Within the Team journal transaction, an existing matching job is flushed and returned even at queue capacity or after completion; mismatched identity inputs are rejected. New jobs resolve the provider spec and compare every pinned input before appending. Thus a moving worker branch or differently configured integration provider cannot silently change the submission. Caller input is snapshotted before awaiting admission. Coordinator submission records and policy linkage now support automatic acceptance; canonical cross-Team integration serialization remains required.

### Durable submissions

The host `WorkspaceCoordinator.submit` operation requires the authorized Lead and the latest terminal attempt's generation/revision, a full source commit ID, and evidence. The attempt must have reported successfully and have confirmed runtime-stop evidence. Cancelled, superseded, unreported, or stopping attempts cannot submit. `submissions.jsonl` records the attempt/task/runtime identity, source commit, evidence, registered repository/target, and verification commands plus policy revision before external queue admission. A persisted UUID serves as both submission and integration identity. Replays require identical immutable inputs.

Pending submissions are reconciled on configured, unpaused startup scans through pinned integration admission. A crash between queue admission and the submission's queued event reuses the same integration ID. Attempt authority is rechecked before each admission. The workspace host view includes submissions. Runtime cancellation rejects work that has already entered integration, because it cannot cancel a verification/promotion job. Integration cancellation, model/Remote submission controls and canonical cross-Team integration serialization remain required.

### Automatic submission and integration execution

When execution and the Team integration provider are configured, scans read the exact HEAD commit of each successful terminal worker’s ready worktree and submit its report as evidence. Existing submission identity prevents redispatch or repinning, and pause/cancellation exclude new submission. Pending submissions retry admission under their recorded policy. The coordinator runs at most one pending integration per Team per scan and only when that next job belongs to a coordinator submission. Provider policy mismatch blocks admission. Verification failure leaves the target protected and records diagnostics; a successful promotion permits the dedicated task-acceptance transition. The Git provider’s existing target-movement and interrupted-verification limitations remain; automatic repair/reverification is required.

### Verified task acceptance and dependency release

The host-only acceptance operation runs inside the Team task transaction. The coordinator must grant the exact task/submission/integration binding, latest terminal attempt, worker, source commit, and registered verification policy. The task board additionally requires a merged job with candidate and target commit evidence and completed prerequisites. It writes a deterministic receipt containing submission/integration/source/candidate/target IDs, then flushes before the submission journal records accepted. Replay of that receipt does not increment the task revision. Ordinary model task mutation remains fenced. Scheduling considers dependencies eligible only when their tasks are completed by this acceptance path; accepted status is explicit in the workspace view. A real-Git diamond DAG now completes without manual dispatch or task completion. Fresh-process ambiguous-promotion, promotion, and task-receipt crash acceptance now passes; in-process midway resumption passes; broader cross-project invariants remain required.

The ambiguous-promotion process barrier runs after the Git provider advances the target but before the integration runner records merged. A fresh process sees the same verified candidate, recognizes that target HEAD already equals it, persists merged, and accepts the task without starting another worker or moving HEAD again. The full-DAG completion barrier waits for both task receipts and submission acknowledgements; the intentional gap between them is covered separately by crash injection.

### Bounded in-process continuation

Before resuming an interrupted, absent DSH runtime, the coordinator bridge records an assignment recovery event containing observed session sequence, count, next eligible time and a random mailbox identity. Recovery retains the active assignment and capacity; the same persisted observation reuses its message identity. New interrupted progress admits at most three rounds, with delays of one, two, and four seconds. The checkpoint prompt directs the worker to inspect preserved artifacts and continue in its existing worktree. Host-only reserved mailbox admission rejects changed content under an existing identity and flushes before acknowledgement. Existing mailbox target receipts prevent duplicate delivery. A pending uncertain delivery remains owned; exhausting three interrupted rounds stops/drains the attempt and leaves a recovery-required outcome.

Fresh-process tests kill an actual in-process worker inside its model request after flushing state and writing an uncommitted edit. Startup resumes the same attempt/runtime, retains that edit, and completes verified acceptance. The dependent-DAG variant also completes all four tasks without duplicate assignments. This does not implement external-process continuation, configurable retry policy, workflow handoff, or operator escalation.

### Canonical integration exclusion

Each Team integration run acquires an OS-backed lock under the canonical Git common directory, keyed by the target branch hash. Aliases, linked worktrees, Teams, and server processes therefore share exclusion for the same repository/target. Ownership spans target observation, verification, promotion and the durable job update, and releases only after those operations settle. Contention rejects with TEAM_INTEGRATION_BUSY before changing the job phase. Lock files remain in place; closing the owning descriptor or process exit releases the flock. This implements shared execution exclusion; globally ordered backlog policy and bounded target-movement/reverification remain unfinished.

### Bounded target-movement re-verification

A verified job whose provider reports `TEAM_INTEGRATION_STALE` transitions to queued with a fresh deterministic `.retry-N` candidate path. The transition appends the exact old cwd, target, candidate and diagnostic to `previousCandidates`, clears only the current target/candidate, and retains the submission ID, worker, repository, source commit and verification commands. History is append-only and capped at three retries; the fourth stale verification becomes failed. Execution yields after persisting retry intent, so a restart or subsequent scan uses the same round and path. Existing records omit history and retain their original semantics. Older binaries reject the new fields through strict persisted schemas; do not downgrade logs containing retry history.

Every earlier checkout remains owned in the projection; an occupied candidate directory fails safely through Git without deleting files. Promotion still runs first for verified jobs, preserving already-promoted recognition. Separate built provider bundles communicate failure through the stable error code, not TeamError constructor identity. Failed verification or interrupted running rounds remain failed with artifacts retained; automatic repair attempts and configurable policy are still separate unfinished work.

### Explicit integration repair attempts

Initial coordinator reservation pins `repairLimit` from `execution.maxRepairAttempts` (default 3, allowed 0–10). A failed integration classified as `verification` can make only its latest, terminal, reported, drained attempt eligible for repair. A separate assignment reservation records the predecessor attempt, submission/integration IDs, pinned source, candidate path, diagnostic and monotonically increasing round before spawning any worker. It retains the original limit, uses a new runtime/worktree and generation, and consumes the existing scheduler's capacity, priority, project fairness, pause and pacing rules. Store replay rejects budget changes, missing predecessors, exhausted rounds and erased repair history. No timer or provider result can reset the budget.

The model receives the repair metadata plus a checkpoint instructing it to apply the pinned source and fix conflicts/checks in the new worktree. Submission and acceptance continue to require the exact latest attempt. Failed source submissions/jobs and candidate directories remain intact; successful repaired acceptance is recorded only against the new submission. Cancellation permits failed historical jobs but rejects integrations which can still promote. Disabled repair and exhausted budgets remain durable blockers. Old attempts without a pinned limit and old unclassified integration failures do not gain automatic repair on upgrade. Older binaries reject the new strict fields on replay, so downgrade requires a compatible backup.

The fresh-process fixture kills the coordinator after repair reservation and before worker creation. Its successor starts the same reserved runtime, receives pinned source context, merges that original source into the fresh worktree, creates the repair, verifies and accepts it. A higher successor configuration does not alter the existing budget. Interrupted repair workers use the existing same-runtime recovery protocol; richer workflow handoff and escalation remain separate milestones.

### Host-only integration review gate

Pinned integration admission may carry an explicit `reviewGate`. The host `approvePinnedIntegration` API accepts a receipt only for the exact verified job and binds the integration ID, source commit, target commit, candidate commit, review gate, and review ID. The configured host authorization callback defaults to deny, so a model, browser, or ordinary Lead operation cannot forge approval. Projection keeps the receipt immutable, requires those fields to match the current candidate, and requires a gated job to carry its receipt before merge. A matching replay is flushed idempotently.

When a gated verified candidate becomes stale, the retry transition records the old candidate and its review receipt in `previousCandidates`, clears the current receipt, and requires a new receipt for the new candidate. Background workers stop at the verified approval boundary and await the host review. This is a host integration gate; workflow runtime and external publication authorization remain separate unfinished work.

### Workflow core and candidate cleanup foundations

`WorkflowStore` persists immutable parameterized JSON definitions and step receipts. Artifact submission, candidate checks, report review, integration, and external publication are separate obligations. Failed review prevents downstream integration. Retry budgets and backoff survive journal reconstruction; publication authorization history is append-only and binds the exact step/revision and actor/evidence.

The initial vertical runtime supports only the bundled `investigation-report@1` report-review template. A workflow creation pre-validates and pins its substituted definition, then records a task-creation intent before calling the host. That intent becomes a stable `workflow-<intent>` Team task ID in the same flushed Team event, so a crash after task creation replays the exact task instead of deduplicating display text. Accepted `ReportStore` receipts alone complete steps; the next managed task receives the accepted report, criteria, rationale, and durable receipt ID. Coordinator scan then uses the ordinary assignment queue to reserve a fresh worker/runtime for that task. Scoped Lead tools and Remote controls create, inspect, and resume these executions.

`GitCandidateCleanup` acquires canonical target ownership and removes only an exactly identified, detached, clean candidate already reachable from the configured target. It includes ignored/untracked content and operation-state checks, never force-removes, and requires path plus registration absence for idempotent recovery. `CandidateRetentionStore` adds a separate durable intent journal behind optional `execution.candidateRetention`: only the current final accepted merged candidate is scheduled, the deadline is pinned at first observation rather than merge time, and pause leaves the intent queued. A running cleanup that is interrupted becomes uncertain and is never automatically retried. The active-provider check covers canonical live in-process Agents only; it does not prove external ownership. Failed or superseded candidates have no retention intent.
