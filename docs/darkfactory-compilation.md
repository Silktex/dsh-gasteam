# Durable compiler preparation and held admission

The host SDK exposes `DarkFactoryCompilationStore` and `DarkFactoryCompilationController` through `dsh-team/darkfactory`. They connect the existing host spec validator to durable admission. The coordinator's observe mode does not invoke them. Compiler calls are injected host callbacks; live provider budgeting, compiler configuration and executing factory modes remain separate work.

Open the compilation store with the registered project, Lead and workflow templates. Its native journal is `darkfactory/<projectId>/compilation.jsonl`. A compilation intent contains the complete `CompilerHostContext`, registered Lead, workflow template/parameters and policy record/decision references. The context must contain the exact current trusted work item, registered executable checks and reproduction evidence, and immutable compiler, policy, model and workflow pins. Store replay reconstructs the context, evaluation and admission plan; a supplied outcome or digest cannot substitute for native validation.

Construct the controller with the compilation and ingestion stores, an existing `DarkFactoryAdmissionController` as `admissions`, and the trusted `authorize`, `compile`, `recover` and `quarantine` callbacks. The quarantine callback must durably create or reuse the matching incident in the existing health inbox before returning its ID.

`controller.compile({ projectId, intent })` persists that intent before invoking the compiler. `controller.resume({ projectId, limit })` reconciles pending records after restart. The controller checks the current source and its injected host authority before compiler work, result acceptance and admission. Registered policy lookup and actual service authority remain obligations of the trusted host callback. A newer revision of the same project/source/entity quarantines while an earlier nonquarantined compilation remains active. Durable creation order preserves the earlier record on restart. Admitted workflows are still held and count as active; an accepted-release reopening path is not implemented yet.

The durable sequence is:

1. Pin the complete intent and deterministic source identity.
2. Record an attempt ID and phase before calling `compile({ attemptId, context, phase, signal })`.
3. Normalize the response, evaluate it with `SpecCompilerSession`, and persist the resulting cursor and outcome atomically. A compiled result includes the complete admission intent.
4. Permit one schema repair using a distinct deterministic attempt ID. Ambiguity, conflict, unsupported work and exhausted repair produce quarantine rather than repeated sampling.
5. Pass the exact persisted admission intent to the existing admission controller. After it confirms all records, persist its matching acknowledged receipt. Tasks retain their immutable factory hold.

A process may die after a compiler returns but before its result is stored. On restart, `recover()` receives the same attempt identity and returns one of three explicit results: `completed` with the original proposal, `definitely-not-started`, or `unknown`. The host must establish these facts using its actual request transport or durable result service. A timeout, missing local response or provider exception is not proof that a request never started. An unknown result quarantines the work with an existing health inbox reference. Only a proven unstarted request permits invocation with that same ID. This protocol does not claim exactly-once provider execution.

The store enforces exclusive ownership, strict bounded events, revision checks, a hash chain and sync-before-publication. Before an attempt starts, it reserves configured result/admission capacity plus terminal headroom; unrelated appends cannot consume that reservation. A result that cannot fit its configured record ceiling becomes digest-only malformed evidence and consumes the normal bounded repair allowance. Physical storage failure still requires recovery. Terminal results and repair accounting survive replay. `DarkFactoryCompilationStore.migrate()` uses the same offline layout protocol and mandatory external-reference validator as the other factory journals. See [offline migration](darkfactory-migration.md).

Malformed responses persist only bounded digest/byte metadata, and negative model explanations become fixed reason codes. Valid spec narrative still needs host sanitization before submission; the validator treats prose as data and cannot classify arbitrary secrets. Raw provider exceptions are not persisted by the controller.

Callbacks receive an abort signal and a deadline configured by `callbackDeadlineMs` (30 seconds by default, at most 60 seconds). `stop()` aborts controller waits; an unresolved compiler or recovery promise prevents another invocation in that controller. A late result does not update a terminal compilation. The existing admission controller has no cancellation signal: a delegated materialization may finish held after the outer deadline. The host must track and settle its actual delegated operations before closing their stores; an aborted wait alone does not prove that an operation stopped.

[Compiler process tests](../tests/darkfactory-compilation-restart.spec.ts) use the built SDK, actual journals and health inbox, with explicit local compiler-result and materialization simulators. They exercise attempt/result/repair/handoff and escalation crash boundaries. [The separate Team process test](../tests/darkfactory-team-admission-restart.spec.ts) kills a real materializer after two native Team task writes, then recovers five stable held tasks and matching acknowledgements. The tests do not call a paid model or enable execution, publication or deployment.
